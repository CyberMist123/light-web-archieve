# 发布标准（Release Bar）

这份文件定义「可以公开发布」的标准：**对外说出去的每一句话，都要在一台干净的 Windows 电脑上做得到**。
任何人（包括 AI 编码助手）改这个项目之前先读这里；判断一项工作「做完」时，按第 3 节的完成定义检查。

状态标记：✅ 已达标 · 🟡 部分达标 · ❌ 未达标。改动影响到哪一条，就在同一个提交里更新那一条的状态和说明。

## 2. 体验预算（P10「丝滑」的量化口径）

以「350 篇收藏、普通笔记本电脑」为基准，括号里是 1000 篇时的预算。

| 项目 | 预算 |
|---|---|
| 打开目录页到封面出现 | ≤ 1.5 秒（≤ 3 秒） |
| 搜索框输入到结果刷新 | ≤ 150 毫秒（≤ 300 毫秒） |
| 打开一篇再返回目录 | 搜索词、筛选、滚动位置、多选状态都还在 |
| 后台同步、补处理进行中 | 页面不闪、不重建、不丢输入；没有内容变化就不重绘 |
| 用户点的每一个操作 | 有明确结果：成功、失败（附原因）、或进行中（显示真实阶段） |
| 正在生成的 AI 回答 | 随时可以停止，停止后不留后台进程 |
| 插件对 Obsidian 启动的拖慢 | ≤ 0.5 秒 |

**新功能不能增加摩擦**：加一个功能，如果让上面任何一项变差，要么优化到达标，要么默认关闭或收进二级入口。

## 3. 每次改动的完成定义

一项修改或新功能，同时满足下面几条才算做完：

1. **后端对**：逻辑正确，单测覆盖，`python -m pytest -q` 全过。
2. **用户看得到**：后端产生的每个新状态（成功、失败、跳过、等待），都写清用户在哪里看到它（页面提示、卡片标记、诊断列表、设置页的一行）。用户主动点的操作要如实告知结果；后台的事按 P12，能看到但不推送。
3. **真实入口验过**：在 Obsidian 里实际操作过，或者跑过真实的同步入口；只有单测通过不算。改动涉及页面时，记下第 2 节相关的预算项实测值。
4. **不倒退**：不让第 1 节任何一条的状态变差，不让第 2 节任何一项超出预算；不新增「仓库外」依赖。
5. **文档同步**：本文件里受影响条目的状态，以及 README 的「边界」节，在同一个提交里更新。**README 和插件说明里面向用户的功能描述，改之前先问项目作者。**

## 4. 发布门槛

1–4 全部满足才公开宣传「装一个插件就能用」：

1. 第 1 节 P1–P12 全部 ✅。
2. 第 2 节体验预算全部实测达标。
3. 测试：pytest 全过；node 和页面测试能一条命令跑起来（仓库带 package.json），并且全过。
4. **陌生电脑验收**：在一台没有作者开发环境的 Windows 上，按 README 走完：安装插件 → 自动准备组件 → 扫码 → 导入一篇 → 同步收藏 → 重启 Obsidian 后仍可用 → 搜到旧收藏 → 查看来源 → 写批注 → 在诊断里看到并补齐一个失败项。另外单独验证：关掉 Obsidian 后定时同步是否照常运行（如果首版只支持 Obsidian 开着时同步，就在 README 里明确写出来）。

达到门槛之前，对外一律称「测试版，需要配置环境」。
